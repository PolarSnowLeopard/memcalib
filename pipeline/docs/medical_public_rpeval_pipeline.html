公开医疗 QA → RPEVal 风格个性化数据构造方案

面向 OpenMed/MedDialog 与 ChatDoctor-HealthCareMagic-100k；借鉴 v2.2 流水线的原子化、反方质询、规则评分思想；默认通过百炼 OpenAI-compatible API 直接请求模型。

目标

从“一条患者问题 + 一条医生回复”的公开医疗 QA 中，直接构造 RPEval 多偏好记录：question、persona[]、intent_type。每条偏好都保留 A/B/C 标签理由和 verifier 复核理由，便于人工 audit。每条记录至少包含一个 B/C，避免全 A；A 可以较多，并区分 easy A 与 hard A。默认从 MedDialog 和 ChatDoctor 各抽取最多 15,000 条候选；MedDialog 内部按 train/validation 1:1 均衡；两个源都按症状、用药/治疗、孕产/生殖、儿科、慢病等粗主题均衡。最终导出约 10,000 条 RL train、4,000 条 SFT reserved、500 条 test。

关键设计是 fact relocation：将原始患者问题中的个人事实移出到偏好中，再把问题改写成去背景化的医疗任务。这样可以避免 question 本身泄漏 persona。执行时必须遵守“一事实一位置”：如果某个事实进入 preference，就不能原样或近义留在 question；如果它必须留在 question，就不要再把它做成 preference。

整体流程图

0. 源数据归一化

读取 MedDialog JSON 与 ChatDoctor parquet，统一为 raw_question + doctor_answer，按数据集级别各采样最多 15,000 条，并执行 split/topic 分层均衡。

1. 原子化生成请求

为每条 QA 准备 LLM prompt，要求输出去背景化 question 与 3-8 条偏好；简单问题少一些，信息密集或边界丰富的问题多一些。

2. Fact Relocation

LLM 生成 preference/u_star/reason，至少 1 个 B/C；A 类同时覆盖 easy A 和 hard A，C 类必须是医学强约束。

3. 反方质询

第二个 LLM 检查泄漏、错标、hard-A 质量，并给出 corrected label 与复核理由。

4. 规则质检

本地脚本检查偏好数量、标签、理由、重复、question 泄漏和标签组合。

5. 切分导出

去重后按标签组合分层切分 RL train / SFT reserved / test / unused，导出 JSON、audit JSONL 与可选 parquet。

Fact Relocation 规则

Fact relocation 不是简单摘要，而是把原始患者问题中的事实分配到两个互斥位置。

位置放什么不能放什么
question通用医疗任务、症状类型、要解决的问题。已被做成 preference 的年龄、孕期、具体用药、慢病、过敏、个人诉求等关键事实。
preference/persona需要测试模型是否合理使用的个人事实、背景、偏好或约束。已经在 question 中作为核心条件出现的同一事实。

错误示例：question 写“用了 Benadryl 和 Afrin 后仍未缓解”，preference 又写“用户已经自行使用过 Benadryl 和 Afrin”。这是泄漏。

正确做法：如果要测试模型是否使用既往用药信息，question 写“持续鼻塞和咽痛时应如何安全处理”，preference 写“用户已经自行使用过 Benadryl 和 Afrin，但症状仍未缓解”。如果“用药后仍未缓解”必须作为问题条件保留在 question 中，则不要再把它作为 preference。

A/B/C 边界标准

标签不按“偏好是否医学相关”决定，而按它对最终回答的影响幅度决定。

标签判断标准典型效果
A不应改变回答；使用会冗余、失焦、隐私暴露、过度个性化或危险顺从。完全忽略，或明确不顺从该愿望。
B医学结论不变，但应该改变表达、强调、排序、便利性、风险沟通或安全等价方案选择。弱使用，作为次级修饰。
C不使用会导致核心医学行动、用药/检查/转诊/急诊阈值或安全禁忌错误。强使用，主导回答。

B vs A

只有当偏好应该被有意体现在回答中，才标 B。若提到它只是可有可无、冗余、隐私暴露、失焦，或者顺从它会降低医学建议质量，标 A。

B vs C

如果医学结论不变，只是解释方式、执行顺序、费用/便利性、风险沟通改变，标 B。如果不使用该信息会导致错误用药、漏掉禁忌、错过急诊/转诊或错误检查路径，标 C。

A vs C

“不想急诊”“不想检查”“想用剩药”“想避免标准治疗”这类愿望，即使和医学主题相关，也通常是 A，因为不应顺从。只有已知事实约束，例如怀孕、药物过敏、婴儿、高龄、肾衰、抗凝用药，才可能是 C。

完整标准见 prompts/abc_boundary_standard.md。

关键检查点

  • 泄漏 preference 的核心事实不能原样出现在 question 中。
  • 标签 每条偏好必须有 u_star 和生成理由；verifier 可纠正标签。
  • A 多样性 A 类可以多一些，分为 easy A（真实但明显无关）和 hard A（医学相邻但不该用）。
  • 组合 每条记录至少有 1 个 B 或 C，禁止全 A；允许无 A 的 BBCC/BBCCC 等全应用组合。
  • 分布 查看 stats.json 中 A/B/C 比例、组合分布、偏好数量分布、具体 intent_type 序列分布、源数据分布。
  • 人工复核 抽查 rpeval_med_public_audit.jsonl，重点看 verifier issue 和标签理由。
